# 同步与缓存规范

更新：2026-10-06，0.18.0。第四批改造已落地。

## 本批规划与结果

| 原有重复 / 问题 | 统一后的实现 | 保留的业务差异 |
| --- | --- | --- |
| 四个 Repository 更新方法重复 IO 调度、锁、验证、状态记录和快照 | `inStore` 管理串行入口；`authenticatedSync` 管理验证 → 读取 → 写入 → 快照 | 每个数据源提供自己的读取和事务写入；消息分页仍有独立游标/合并规则 |
| 四种刷新方法重复重试、恢复缓存、错误处理和进度结算 | ViewModel 的 `syncResource`；所有完整/单项/分页刷新通过同一执行入口 | 课表首次加载/离线文案、其他资源过期提示、更早消息失败标记 |
| 缓存转换与错误写入散落在 ViewModel | `TimetableState.kt` 保存状态类型、`withCache`、`withIssue`、`resourceFailed` | 缓存只替换持久字段，不清除其他资源的错误、进度、加载状态 |
| 重试策略与页面状态操作混在一起 | `SyncRetry.kt` 执行一次资源的重试，通过回调报告重试序号 | 只重试 IO、408、5xx；每项最多三次尝试、延迟 2 秒 / 5 秒 |
| 多个查询分开拼接缓存快照 | DAO `snapshot` 的 Room 读事务 | schema 5 和各资源独立写事务沿用；网络请求不占数据库事务 |
| 阻塞读取结束时协程可能已经取消 | 验证后和写入前检查协程取消状态 | 退出仍先 cancelAndJoin 再清 session 与缓存；不声称 HTTP 阻塞立即中断 |

不引入新的依赖、泛型资源插件、并发同步、数据库迁移或新 API。公开 TimetableStore / StudentApi 方法保持兼容；数据源仍逐个调用 `/user/info` 检查账户。

## 必须保持的规则

- 冷启动先读本地快照，再正常刷新；失败恢复旧缓存，空列表是否已加载由同步时间判断。
- 完整刷新顺序由 SyncResource 声明：Timetable、Coursework、Messages、Library、Modules、Account。验证过账户的课表解析失败仍可继续其他资源；尚未确认账户或会话过期时停止后续工作。
- 账户变化在下载之前清除全部持久数据；验证回调将快照和用户身份一次写入页面状态。所有缓存/更新/退出入口共用 Repository 锁，完整任务只允许一份运行。
- 单资源刷新只清自己的失败提示、只更新对应进度，不再次提示其他资源的旧错误。重试等待不重复计数；认证完成为半步，结果成功或最终失败为整步；提前停止不补满。
- 消息只在用户要求时分页；重试沿用游标。更换账户后旧游标先被拒绝，不发分页请求。合并保持排序、去重、最多 500 条；已有 ID 查找使用集合，拒绝有条目但没有推进的页面。
- 登录失效、解析失败、其他 4xx（包括 429）不自动重试；成功资源不再次下载。
- UI 组件只发送动作、读取状态；重试预算只在 SyncRetry 中，账户与持久化只在 Repository/DAO 中，页面失败转换集中到 TimetableState。

## 验证边界

21 项既有同步/恢复 JVM 检查加 2 项 Repository 编排检查通过。新增检查仅覆盖复杂边界：换账户后清空快照并拦截旧游标；取消阻塞下载后禁止写入且本地退出可完成。Repository 检查使用内存 DAO fixture，不代替 SQLite 事务验证；Room 生成实现已确认包装 snapshot 事务，真实运行还需物理手机的启动/刷新与用户手动反馈。

不新增 UI Test，不修改或运行 Android instrumentation。手动重点：冷启动缓存、正常/重复下拉、断网保留数据、联网恢复、Data status 单项刷新、Messages 更早分页；真正退出仅在用户愿意重新登录时验证。
